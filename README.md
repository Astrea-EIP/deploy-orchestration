# deploy-orchestration

`deploy-orchestration` defines the deployed state of Astrea-EIP environments.
It owns environment configuration, validation, and promotion workflows.

## What belongs here

This repository owns:

- environment files for `preprod` and `prod`
- validation scripts for deployed versions
- promotion workflows between environments
- repository-local orchestration documentation

This repository does not own:

- application business logic
- frontend, mobile, backend, or engine feature code
- central contribution rules

## Local development

Use the validation tooling when changing environment files.

```bash
python scripts/validate_env.py environments/preprod.yml
python scripts/validate_env.py environments/prod.yml
```

## Running the whole stack locally

`docker-compose.yml` starts the full Astrea stack in one command: MongoDB,
the GraphHopper routing engine, `api-back`, and `app-web`.

Prerequisites:

- Docker and Docker Compose installed.
- All six Astrea-EIP repositories cloned as siblings under the same parent
  directory (`docker-compose.yml` builds each service from `../<repo>`).
- A one-time manual step: download an OSM extract covering your test area
  (for example the Pays-de-la-Loire extract from
  [Geofabrik](https://download.geofabrik.de/), consistent with Epitech
  Nantes) and place it at `data/map.osm.pbf`. This file is intentionally not
  committed (too large) and GraphHopper will not start without it.

```bash
docker compose up --build
```

Exposed ports: `app-web` on `4200`, `api-back` on `5217` (Swagger at
`/swagger`), GraphHopper on `8989`, MongoDB on `27017`.

To check everything actually started correctly:

```bash
curl http://localhost:8989/health   # -> OK
curl -I http://localhost:5217/swagger/index.html   # -> 200
curl -I http://localhost:4200/                      # -> 200
```

To stop and remove everything (containers, network, MongoDB volume):

```bash
docker compose down -v
```

This is for local development/demo purposes. It's separate from `api-back`'s
own `docker-compose.yml`, which only starts a disposable MongoDB for backend-only
development — see `api-back/CONTRIBUTING.md`.

### Running from published images

`app-web`, `api-back`, and `core-moteur` (GraphHopper) each publish a
production image to GHCR on every version tag (see each repo's
`.github/workflows/publish-image.yml`). `docker-compose.prod.yml` runs the
whole stack from those images instead of building from source — this is
what a real deployment (preprod/prod) will use.

```bash
docker login ghcr.io -u <your-github-username>   # once, packages are private
python scripts/render_env.py environments/preprod.yml > .env
docker compose -f docker-compose.prod.yml --env-file .env up -d
```

The same health checks as above apply. Stop with
`docker compose -f docker-compose.prod.yml down -v`.

Still plain Docker Compose — no Kubernetes or Terraform at this team's scale.
Remaining work before a real server deployment: a reverse proxy (Caddy) for
HTTPS, a full (not test-sized) OSM extract, and the SSH-based deploy workflow
itself (see `deploy-orchestration#10`).

#### `.env` and secrets

`scripts/render_env.py` only ever writes deployed **version tags** — the
same values already committed in `environments/*.yml`, so this `.env` holds
nothing sensitive. It stays untracked (see `.gitignore`) purely because it's
a generated file, not because of its content.

Once real secrets are needed on a server (database credentials, a GHCR pull
token, etc. — see `deploy-orchestration#10`), keep them in a **separate**
file from this one (for example `.env.secrets`), written once by hand on the
server, never generated by a script, `chmod 600`, owned only by the deploy
user. Prefer GitHub Environment secrets for anything the deploy workflow
itself needs at deploy time, so it never sits on disk between deployments.

## Rules

- Use `version` everywhere for deployed references.
- Do not introduce `ref`.
- All changes must go through pull requests.
- `prod` changes must stay traceable to validated preprod state.
